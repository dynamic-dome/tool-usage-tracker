# CAPABILITIES
- Aufzeichnen: `PreToolUse` + `PostToolUse` als JSONL (`phase:"pre"`/`"post"`), inklusive `ts_utc`, `ts_local`, `agent`, `tool_name`, `session_id`, `tool_use_id`, `cwd`, `project`, `is_git_repo`, `hook_event`, `summary`, `ok`, `error`, `schema_v`.
- Sanitisierung: 120-Zeichen-Limit, Secret-Redaction, Pfad-Kürzung, kein Datei-Inhalt. Abgedeckte Token-Formate u.a. OpenAI (`sk-`/`sk-proj-`), AWS (`AKIA/ASIA`), GitHub (`gho_/ghu_/ghs_/ghr_`/`github_pat_`), Slack (`xox[baprs]-`), Google API-Key (`AIza…`), Stripe Secret/Restricted (Live **und** Test, `[sr]k_(live|test)_…`, S-01), GitLab PAT (`glpat-…`, S-01), Google OAuth2 (`ya29.…`, S-01), JWT (`eyJ…`) und generische `key=value`-Zuweisungen.
- Pairing: `analysis/_load.py` verschmilzt Pre/Post zu Spans mit `duration_ms`, Erfolg und Fehlertext; exakter Match per `tool_use_id`, FIFO-Fallback fuer Altdaten.
- Auswertung: CLI-Report, statisches HTML-Dashboard und Live-Dashboard (`analysis/server.py`) mit Analytics-/Timeline-/Compare-Ansicht, Filtern und manueller Refresh-Steuerung.
- Skill-Erfassung (seit 2026-06-16): `build_summary` traegt fuer das `Skill`-Tool den Skill-Namen (`tool_input.skill`) ins `summary` — der bestehende `PreToolUse`-Hook erfasst damit, WELCHER Claude-Code-Skill (inkl. Slash-Command) genutzt wurde, nicht nur `tool_name=Skill`.
- Skill-Nutzungs-Report: `python analysis/skill_usage.py` (`skill_usage_stats()`) aggregiert die `Skill`-Calls pro Skill (Aufrufe, Projekt-Streuung, letzte Nutzung) mit global-vs-lokal-Heuristik (≥2 Projekte → global-Kandidat, 1 → lokal); zaehlt nur Pre-Events (Dedup gegen Post). Datengrundlage fuer behalten/deinstallieren + global/lokal-Split der installierten Skills. Nie genutzte Skills erscheinen nicht (gegen die Skill-Liste gegenchecken).
- Timeline/Waterfall: der Timeline-Tab gruppiert Spans pro Session in Turns (global-adaptive Gap-Heuristik, median+3*MAD, Klammer 5-120s, Fallback 30s) und stellt sie pro Turn auf einer echten Zeitachse dar (x=Offset ab Turn-Start, Breite=Dauer); gleichzeitige Spans werden vertikal gestapelt.
- Kosten/Token (A-1): der Loader liest optionale `input_tokens`/`output_tokens`/`cache_read_tokens`/`cost_usd` pro Span und aggregiert sie via `cost_breakdown()` (Summen + `cost_by_tool`/`cost_by_agent` + `has_cost_data`); das Dashboard zeigt Σ-Kosten/Σ-Tokens-KPIs + Kosten-pro-Tool-Panel nur bei vorhandenen Daten. `analysis/ingest_otlp.py` parst Claude-Code-OTLP-Metrics (console + OTLP/JSON) zu `usage_by_session.json` (Kosten nur pro Session, da Metrics keine `tool_use_id` tragen). Die Σ-KPIs deduplizieren über `request_id` (Turn-Token werden je Turn nur einmal gezählt, auch wenn mehrere Tool-Calls sie geerbt haben).
- Token im Abo-Modell (ccusage-Ingest): `analysis/ingest_ccusage.py` liest Claude Codes lokale Session-JSONL aus `~/.claude/projects/<hash>/*.jsonl` (Env `CLAUDE_PROJECTS_DIR`) — kein API-Key, keine Telemetrie-Aktivierung nötig (dieselbe Datenquelle wie das Community-Tool `ccusage`). Token werden **pro `requestId`/Turn** erfasst (eine `usage`-Summe pro Denk-Schritt, kein Pro-Call-Aufsplitten) und nach `data/tokens_by_request.json` geschrieben; eine Offline-Preistabelle pro Modell liefert den **rechnerischen USD-Gegenwert** (im Abo zahlt man die Flatrate). Der Loader joint die Turn-Token über `tool_use_id` an die Spans (`enrich_spans_with_tokens`, markiert `turn_tokens=True`); der Live-Server reichert automatisch an, sobald die Datei existiert (Env `TOOL_TRACKER_TOKENS`), und das A-1-Cost-Panel rendert dann ohne weitere Konfiguration.
- JSONL-Rotation: der Hot-Path rotiert `data/events.jsonl` bei ≥ Schwelle (Default 5 MB, Env `TOOL_TRACKER_MAX_BYTES`) zu `events.N.jsonl` — rein additiv und fail-safe (exit 0 bleibt garantiert). `load_events` liest die aktive Datei plus alle `events.*.jsonl`-Teile transparent zusammen (älteste zuerst) und bietet einen optionalen `tail=N`-Parameter für große Datenbestände.
- Run-Comparison (B-3): `comparison(spans, key='agent'|'session_id')` aggregiert pro Gruppe Tool-Calls, gepaarte Spans, Fehlversuche, Erfolgsrate, Gesamtdauer, Risk-Verteilung, mutierende Aktionen und Gesamtkosten; das Compare-Tab markiert pro Metrik besten (grün) und schlechtesten (rot) Wert.
- Drift/Spend-Score (D-3): `drift_breakdown(spans)` misst pro Session, wieviel Arbeit abseits des dominanten Themas (häufigste `app`/`intent`) floss — `drift_ratio` (Anteil Off-Task-Calls) und `spend_drift_ratio` (kosten-gewichtet, turn-dedupliziert), plus separat gezählte mutierende Off-Task-Aktionen (`off_task_mutating`). Datei-/Such-/Agent-/Web-Tools werden dafür im Auswerte-Pfad klassifiziert (`_span_app_intent`, Hook unberührt). Das Dashboard zeigt eine nach Spend-Drift sortierte Tabelle (≥5 klassifizierte Spans), Drift ≥50% rot / ≤20% grün, mutierende Off-Task-Spans rot.
- Ad-hoc-SQL (B-6): `analysis/sql.py` bietet ein optionales DuckDB-Add-on (lazy importiert) mit zwei Views `events` (roh) und `spans` (in SQL gepaart) inkl. Window-Functions; fehlt `duckdb`, endet die CLI sauber mit Exit 3 + Hinweis statt Crash — der Kern bleibt stdlib-only.
- OTLP-Trace-Export (Teil C): `analysis/otlp_export.py` mappt gepaarte Spans auf OTLP/JSON-`resourceSpans` (gen_ai.*-konform, Trace = Session, Span = Tool-Call, deterministische IDs) und kann sie optional an einen lokalen OTLP/HTTP-Collector POSTen (Graceful-Fallback bei nicht erreichbarem Collector); strikt stdlib-only, Hot-Path unberührt.
- Bash-Klassifizierung: `PreToolUse`-Events fuer `Bash` bekommen optionale Felder `app`, `operation`, `intent`, `risk`, `mutating` fuer bekannte CLI-Familien (`git`, `gh`, `wrangler`, `notebooklm`, Python-/Node-Tools).
- Kontext-Felder (A-5): in einem Git-Repo wird `git_branch` aus `.git/HEAD` ergaenzt (reiner Dateiread, kein subprocess; Detached HEAD -> 7-Zeichen-Hash). Datei-Tools (`Read`/`Write`/`Edit`/`NotebookEdit`) bekommen `file_ext` (Endung, lowercase).
- Codex: projektlokale `.codex/hooks.json` vorhanden; Payload-Erkennung ueber `model` schreibt `agent:"codex"`. Live-Discovery in `codex exec` ist noch nicht voll bestaetigt.
